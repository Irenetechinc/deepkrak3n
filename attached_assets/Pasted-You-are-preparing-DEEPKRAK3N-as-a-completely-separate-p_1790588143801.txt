## Required API contract with AdRoom

The AdRoom backend already calls DEEPKRAK3N as an external HTTP service.

Do not change the contract unless absolutely necessary.

### Health check

Implement:

GET /health

Expected response:

HTTP 200

{
  "status": "ok",
  "service": "deepkrak3n"
}

The endpoint must be fast and must not run a username search.

It must return a non-200 response only when the service process itself is unhealthy.

### Username search

Implement:

POST /api/search/username?username=<USERNAME>&limit=30

Example:

curl -X POST \
  "https://<deepkrak3n-railway-domain>/api/search/username?username=public-user&limit=30" \
  -H "Accept: application/json"

The request may have an empty body. Do not require a JSON body.

The endpoint must:

- Accept a public username
- Validate and sanitize the username
- Apply a safe maximum result limit
- Default to 30 results when no limit is supplied
- Return only publicly available profile discovery results
- Never require a logged-in social media session
- Never require cookies from AdRoom
- Never access private accounts
- Never collect private messages, passwords, session tokens, or private contact data
- Never use credential stuffing, account takeover, or authenticated scraping

The preferred response format is:

{
  "results": [
    {
      "username": "public-user",
      "site": "example",
      "platform": "example",
      "profile_url": "https://example.com/public-user",
      "url": "https://example.com/public-user",
      "status": "found",
      "bio": "Optional public profile description",
      "description": "Optional public description",
      "text": "Optional public summary"
    }
  ]
}

An empty result must be a successful response:

{
  "results": []
}

The AdRoom adapter can also normalize these response formats:

- A top-level JSON array
- `{ "results": [...] }`
- `{ "data": [...] }`
- `{ "items": [...] }`
- `{ "found_profiles": [...] }`

Make the response deterministic and JSON serializable.

Each returned record should expose at least one usable public URL using one of these fields:

- `profile_url`
- `url`
- `url_user`
- `href`
- `link`
- `permalink`

The AdRoom backend uses those URLs to create public-profile discovery evidence.

## Error handling

Use clear HTTP responses:

- 400 for missing or invalid usernames
- 400 for invalid limits
- 429 when rate limiting is triggered
- 500 for unexpected internal errors
- 503 when the search engine is unavailable

Do not return stack traces, environment variables, credentials, filesystem paths, or internal exception details to clients.

Log useful server-side diagnostic information with standard Python logging, but never log secrets or private user data.

## Runtime and reliability requirements

The service must be production-safe on Railway:

- Read `PORT` from the environment
- Bind to `0.0.0.0`
- Do not hardcode localhost
- Do not assume a fixed port
- Use request and subprocess timeouts
- Prevent indefinitely running searches
- Clean up temporary files
- Avoid memory leaks
- Handle concurrent requests safely
- Return JSON for all API responses
- Avoid blocking the event loop where possible
- Use bounded concurrency so multiple searches cannot exhaust the Railway instance
- Make `/health` independent from the search engine
- Fail clearly if a search dependency is unavailable

If the existing Deepkrak3n implementation invokes a command-line tool, isolate each request in a temporary directory, enforce a timeout, capture structured output only, and remove the temporary directory in a `finally` block.

Do not auto-install packages or clone repositories during a user request. All required dependencies must be declared in `requirements.txt` and installed during the Railway build.
